# Critical review — offline prototype only

Review method: adversarial scenarios written separately from the happy-path fixtures; source and data-flow inspection. **Not** an independent third-party audit or second model's verification.

## Finding S-001 (HIGH): Signed-but-false decision

The first implementation checked event envelope signatures, parent workload binding and hash-chain anchoring, but **not the correctness** of a signed evaluator's `OK` claim. A buggy/compromised authorized signer could claim `OK` despite drift and pass crypto-only verification.

**Fix implemented:** add `verify_decision_semantics` which independently recomputes the result from authenticated parent claims at separately supplied clock and pinned policy version. CLI `verify` now requires both crypto and semantic verification. New regression `test_valid_signed_but_false_decision_rejected_by_independent_recomputation` demonstrates cryptographic success but semantic rejection. Retested.

## Finding S-002 (MEDIUM): Unhashable reference crash

Malformed `refs` containing non-string elements could throw instead of returning invalid proof. **Fix:** explicit type guard before constructing a set; attack test added.

## Finding S-003 (MEDIUM): Ambiguous JSON and unbounded local files

Default `json.loads` accepted duplicate keys with last-key-wins semantics and nonstandard `NaN`/`Infinity`; local inputs had no file-size limit. The verifier also assumed a mapping-shaped trust store and a syntactically valid external anchor.

**Fix implemented:** reject duplicate keys at all nesting depths, nonfinite numeric tokens, invalid UTF-8 and files larger than 8 MiB; bound accepted journal event count to 10,000; validate trust type and external head form. Added CLI, parser, malformed-trust and malformed-anchor regressions. These are offline PoC limits, not a comprehensive parser/DoS threat model.

## Outstanding material risks (not resolved here)

- **Trust root / head:** demonstration writes keys/checkpoint alongside journal; an attacker replacing all three could defeat detection. External WORM/transparency anchoring and identity/key rotation are mandatory for any real service.
- **Truth vs authenticity:** signed observations and `model_confidence=verified` are only *claims* from a synthetic source. No live k8s-aibom signature verification, artifact trust verification, model-execution attestation, or cluster authorization exists.
- **Time:** freshness relies on an externally trustworthy UTC clock; local test fixed time is a deterministic fixture, not a clock attestation.
- **Sampling/coverage:** untracked namespaces, unsupported workload kinds, pending pods, incomplete digests and unresolved models cannot be declared clean. Cluster-wide informer read scope creates real sensitive metadata exposure.
- **Race/consistency:** cross-plane snapshot versioning, event lag/ordering, revoked identities, resync and recovery are not implemented on real APIs. No concurrency tests, source-authentication tests or Byzantine failure model.
- **Availability/DoS:** a coarse 8 MiB per-file limit and 10,000-event cap now exist; nested JSON depth, aggregate input size, process limits and streaming/load-shedding for hostile multi-tenant input are NOT addressed. Expose nothing to production.
- **Portability:** simple `json.dumps(sort_keys=True)` is a local canonical encoding contract, not RFC 8785 or Sigstore's protocol. Do not interoperate or advertise it as Sigstore-compliant.

Review disposition: acceptable **only** as a synthetic local research checkpoint. No production sign-off.

## M1 self-critical review (2026-11-12)

- **S-004 – Assertion laundering through AIBOM summary:** A controller status with `models[].signed=verified` could make a naive adapter label model identity as cryptographically verified without actually validating its signature or source trust. **Mitigation:** the offline AIBOM adapter deliberately preserves at most `declared`/`inferred`, always leaves missing hashes empty and emits `CR_PROVENANCE_NOT_AUTHENTICATED`. Verified identity is still BLOCKED pending trusted Sigstore/bundle verification and upstream correlation.
- **S-005 – Inconsistent CR/BOM claims:** `Ready=True` can coexist with generation skew, `Stale=True`, wrong workload coordinates, or corrupted inline BOM. **Mitigation:** version pin, coordinate matching, generation and condition gate, hash/size and CycloneDX JSON shape check; unhealthy resources return no usable observation. Matching digest only proves self-consistency of the untrusted CR + inline BOM; it is not authenticity.
- **S-006 – Extraneous signed decision claims:** a signed decision could include additional unevaluated marketing/security fields and still pass core-field recomputation. **Mitigation:** semantic verification now rejects unexpected decision keys. **Residual:** a compromised role key or compromised independently supplied trust root remains outside the PoC trust boundary.
- **Self-review limitations:** These checks are adversarial tests written by the implementer, not independent red-team review; no actual K8s CR exported, no Sigstore signatures verified, no alternate JSON parser used, no real measurement of watch/poll latency.

## S-007 — CI trust boundary (M2, 2026-11-12)

- Public PRs can execute untrusted repository test code. This CI deliberately uses only `pull_request`/`push`, a read-only `GITHUB_TOKEN`, `persist-credentials: false`, no repository secrets, no `pull_request_target`, no external attestations, and no GitHub write scopes. An attacker can still consume allowed public CI resources; branch rules and fork approval are externally controlled.
- First-party actions are pinned to Git object commit SHAs fetched from official GitHub tags (2026-11-12); updates require explicit review. Standard runners are free for public repositories according to GitHub documentation, but only standard `ubuntu-24.04` is used, never a paid larger runner.
- PyPI packages and setuptools build dependencies are version-constrained but **not checksum-locked**; a compromised package index/artifact or malicious contributor may still affect job execution. CI does not run with secrets, but these are not sufficient controls for trusted production publishing. No SBOM, provenance attestation or reproducible wheel builds are claimed.
- A passing CI pipeline verifies synthetic source behavior and deterministic smoke contracts only; it does not authenticate AICR exports, provide an independently held journal checkpoint or prove GPU workload execution.

## M3 self-critical review (2026-11-12)

- **S-008 – Forged recipe pin masquerading as trusted qualification (HIGH, residual):** the CLI accepts both a recipe file and a pin from the user; an attacker controlling both can create an internally matching pair. The code now checks exact byte equality to a separately supplied intent fingerprint, but it does **not** authenticate the pin, publisher, NVIDIA recipe qualification or actual installation. **No `OK` may be inferred from this step.** G4 requires independent source integrity and source-specific attestations.
- **S-009 – JSON exponent overflow to infinity (MEDIUM, fixed in local parser):** Python JSON's `parse_constant` rejection of literal `NaN`/`Infinity` does not catch `1e999` interpreted as floating infinity. A shared bounded strict parser now rejects nonfinite numbers at every depth, with tests for CLI, AICR recipe and inline CycloneDX. Bounded reads avoid a stat/read race for local input size. Remaining risks: deeply nested JSON, huge aggregate files, source-authentication, and parser differential across languages.
- **S-010 – Cross-plane claims are not execution proof (HIGH, residual):** a valid recipe digest does not establish GPU node state, successful installation, model/image digest, fresh inference, or permission scope. AIBOM summary model identity and readiness are separately untrusted. `correlate-offline` can only return `UNKNOWN` on the provided synthetic fixture. Its labels must not be used as production enforcement decisions.
- **Review independence:** this remains implementer self-review plus repeatable adversarial tests, not an independent red-team or third-party review. No actual AICR CLI run, GPU, Kubernetes cluster, or Sigstore verification was performed.

## M4 self-critical review: replay receipt (2026-11-12)

- **S-011 – Python bool/int JSON type confusion (HIGH in replay verifier, fixed):** `dict` equality considers `True == 1`; a forged `component_count: true` passed equality against the correctly recomputed numeric `1`. An adversarial regression demonstrated a passing forged receipt before remediation. Verification now compares canonical JSON *bytes*, preserving JSON types, and rejects malformed/nonfinite records. `canonical` remains a private Python encoding contract, **not** interoperable Sigstore/JCS canonicalization.
- **S-012 – Accidental evidence overwrite (MEDIUM, fixed):** a report output path equal to a source/old report could clobber original bytes. Receipt output now uses exclusive-file creation (`xb`), refusing existing files and symlinks. This is not a transactional/atomic high-availability store; partial outputs on I/O failure require manual discard. Tests prove prior files stay unchanged on collision.
- **S-013 – Source/pin rebind and replay trust (HIGH, unresolved):** an attacker controlling intent, recipe, pin, AIBOM and receipt can construct a new self-consistent receipt; exact hashes and recomputation do **not** detect this without separately trusted origin, clock and external pin. Nor does replay prove `lastReconciled` is an inference execution timestamp. The `verified_replay` CLI flag means internal computation replay only; G4 must verify upstream identity/signatures and source-capture authorization. No new keys or attestation authority were invented.
- **S-014 – Error handling / availability (RESIDUAL):** malformed source during replay returns a structured negative `SOURCE_OR_PIN_INVALID`; create mode rejects invalid input. Source files are each limited to 8 MiB; full streaming, cross-file TOCTOU races, deep parser nesting and aggregate DoS remain unaddressed. Results are not production assurance, and review is implementer self-review rather than external independent security sign-off.

## M5 critical-review notes: fair comparison and hidden conditions (2026-11-12)

- **S-015 – Inflated positive labels (finding, documented):** the older synthetic score counts `DRIFT`, `STALE` and `UNKNOWN` alike as needing attention. That is *not* confirmed-drift recall. M5 introduces independent synthetic latent ground-truth scenarios and reports drift-only detection separately. Missing/stale/future evidence deliberately yields `UNKNOWN`/`STALE` and cannot certify hidden drift.
- **S-016 – False novelty from weak local baseline (finding, documented):** the intentionally naive two-string baseline is not an implementation of AICR, k8s-aibom or any recommended integrated solution. An independently coded comparator using the same normalized complete input has 0 disagreement on the M5 constructed scenarios. This refutes **algorithmic novelty on these inputs** but cannot decide whether authenticated cross-source collection/replay solves a useful real integration problem. Upstream tool comparison remains unperformed.
- **S-017 – Synthetic verification is a label, not a trust root (residual):** the M5 `verified` flag is input data; tests do not verify a Sigstore signature, attested GPU execution or trust-chain publisher. Synthetic repeats vary names rather than independently sampling deployments; do not calculate statistical confidence intervals or extrapolate workload coverage.
- Review independence: implementer self-review and repeatable negative-control tests only, not an external independent assessment.
- **S-018 – Attacker-controlled matching source passes (HIGH, known and unremediated):** an attacker with control of all normalized observation fields can supply identical expected hashes and `model_confidence=verified` while hidden runtime truth differs. The evaluator yields `OK` because no independently authenticated source provenance is in its contract. M5 explicitly constructs this probe and records `security_gate_passed=false`; it is NOT included in the 600-case ordinary coverage metrics. No safe production `OK` claim is possible without trusted source attestation. This cannot be corrected by hashing, replaying, or signing a self-asserted receipt.

## M6 S-018 containment and adversarial review (2026-11-12)

- **Original exploit reproduced (RED):** a complete matching normalized observation with `model_confidence=verified` produced `OK` despite originating in a user-controlled JSON fixture. Raw source identity, cryptographic producer signature and independent trust root were unchecked. The original M5 result `security_gate_passed=false` remains retained as historical evidence.
- **Containment implemented (scoped):** unsigned or merely replayable input cannot produce an authenticated `OK`/`DRIFT` via `evaluate()`: it yields `UNKNOWN/SOURCE_AUTHENTICITY_UNVERIFIED` unless already `STALE` or otherwise unavailable. `evaluate-authenticated` verifies an exact-byte detached Ed25519 assertion under a separately pinned authority plus intent, enforced signer ID, scope, timestamp binding, externally held sequence/head and current clock. It returns a proposed *next* checkpoint; it does **not** write or anchor that checkpoint.
- **Attack tests:** substituted public keys/manifest with unchanged external pin, alternative trusted signing key, tampered observed bytes, corrupted signatures, signed wrong scope/source/key/timestamp, duplicate-key JSON, modified intent hash, altered sequence, replayed old sequence, forked predecessor/head, future/stale sources, signed but `declared` model and retained local journal tamper tests must fail closed. Clean pinned fixture must produce a bounded source-authenticated assertion for positive control.
- **Integrity is not authenticity:** source-local BOM hashes, AICR recipe pin equality, cross-plane receipt replay, and local signed journal chains provide *integrity/consistency* conditional on inputs. Source authenticity additionally requires a verified key-to-identity authorization pinned outside the source; even then, a signature proves only that the key signed a statement. Original data may be fabricated by a compromised **authorized** signer.
- **HIGH residual — trust bootstrap:** this research CLI takes external expected hashes and checkpoint values as arguments. An attacker who controls both documents **and** these independent pins can bootstrap their own authorized key and return `OK`. Enforce separation with independently controlled policy distribution and durable, anti-rollback state in any future deployment. Colocated files in synthetic tests are not proof of independence.
- **HIGH residual — collection truth and model identity:** a legitimate signer can falsely report a digest or `model_confidence=verified`; no actual Sigstore model-signature validation, attested runtime process measurement, secure workload telemetry or verified NVIDIA/Google source credentials have been performed. Treat any synthetic `OK` as *authenticated source-claim agreement only*.
- **Operational residual:** the Python-specific sorted-key JSON signable encoding is neither RFC 8785 nor standard DSSE; trusted time is caller-supplied, key rotation/revocation is manual by changing externally pinned manifest, checkpoint storage is absent, concurrent CAS/reorg protection not implemented, private signing key custody is out of scope. Large/wildly nested input and availability remain bounded only by the current PoC parser/limits.
- **Review status:** implemented and attacked by the same engineering process, with automated regressions. No independent human security reviewer, external red team, Sigstore verification or G4 cluster verification was available; **third-party adversarial sign-off remains pending**. Suggested independent challenges: trust-pin substitution during bootstrap, concurrent same-sequence deliveries, authorized signer compromise, key rotation/revocation, parser differentials, rollback after lost checkpoint, and indistinguishable runtime lies. Do not claim production readiness.
